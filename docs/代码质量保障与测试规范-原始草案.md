# 代码质量保障与测试规范（Code Quality & Testing）

## 1. 总体原则

本项目采用专业 Python 后端工程的代码质量保障体系，遵循以下原则：

- **静态检查、类型检查、自动化测试、集成测试和 CI 相互配合，不得互相替代。**
- 新增或修改业务逻辑时，应同步编写或更新对应测试用例。
- 优先保证代码的正确性、可读性、可维护性和类型安全。
- 测试应覆盖正常场景、边界场景和异常场景，不得仅验证 Happy Path。
- 优先使用成熟、稳定、主流的技术栈，避免重复引入功能相同的工具。
- 不得为了通过检查而随意删除测试、屏蔽异常、滥用 `# type: ignore`、`# noqa` 或降低全局检查标准。
- 所有工具配置优先集中管理于 `pyproject.toml`，避免重复配置。

## 2. 技术栈规范

### 2.1 静态代码质量

- **Ruff**：负责 Lint 检查、代码格式化和 import 排序。
- **Pyright**：负责静态类型检查，初期采用 `standard` 模式。
- Ruff 和 Pyright 必须配合使用，不能互相替代。

推荐命令：

- `uv run ruff check .`
- `uv run ruff format --check .`
- `uv run pyright`

需要自动修复时可以使用：

- `uv run ruff check --fix .`
- `uv run ruff format .`

自动修复后必须检查变更，避免引入非预期修改。

### 2.2 自动化测试

统一采用以下技术栈：

- **pytest**：核心测试框架。
- **pytest-asyncio**：运行基于 asyncio 的异步测试。
- **unittest.mock**：使用 Mock、AsyncMock、patch 隔离外部依赖。
- **HTTPX**：辅助进行 FastAPI HTTP 接口测试。
- **pytest-cov**：统计代码覆盖率和分支覆盖率。

HTTPX 是 HTTP 客户端，不应将其视为 pytest 的替代品。

对于异步测试，优先统一使用 `pytest.mark.asyncio`，避免无必要地混用 pytest-asyncio 和 AnyIO 测试机制。

### 2.3 数据库集成测试

- 使用 pytest + SQLAlchemy + 独立 MySQL 测试数据库。
- 可以使用 Docker Compose 或 Testcontainers 管理测试环境。
- 测试数据库必须与开发数据库、生产数据库严格隔离。
- 不得用 Mock 替代所有数据库集成测试。
- 关键数据库行为必须使用真实数据库验证。
- 必须关注事务提交、回滚、唯一约束、外键约束及 Alembic 迁移。

### 2.4 安全与持续集成

根据项目需要逐步引入：

- **pip-audit**：依赖安全漏洞检查。
- **Bandit**：Python 静态安全分析。
- **GitHub Actions 或其他 CI 平台**：自动执行质量检查与测试。
- **pre-commit**：提交前自动执行轻量级检查。

不应为了增加工具数量而无条件引入所有工具。

## 3. 测试目录规范

测试代码统一放在项目根目录的 `tests/` 下。

推荐组织方式：

- `tests/conftest.py`：公共 fixtures、测试依赖和测试环境初始化。
- `tests/unit/`：单元测试。
- `tests/api/`：FastAPI 接口测试。
- `tests/integration/`：数据库和其他组件集成测试。

文件命名遵循 `test_*.py`，测试函数命名遵循 `test_*`。

测试文件应根据被测试模块命名，例如：

- `test_stock_service.py`
- `test_stock_repository.py`
- `test_stocks_api.py`
- `test_indicators.py`

不得将测试逻辑随意混入正式业务代码。

## 4. 测试用例设计规范

### 4.1 基本要求

每项关键业务功能至少考虑以下三类测试：

1. **正常测试**：验证合法输入产生正确结果。
2. **边界测试**：验证空值、零值、极值、临界条件等。
3. **异常测试**：验证非法输入、资源不存在、外部依赖失败等情况。

测试必须包含有意义的断言。

不得只调用函数而不验证结果，也不得使用无意义的 `assert True` 代替业务验证。

### 4.2 单元测试

- 优先测试 Service 层的核心业务逻辑。
- 尽可能保持测试快速、独立、可重复。
- 使用 `pytest.mark.parametrize` 管理多组输入。
- 使用 `pytest.raises` 验证预期异常。
- 对外部 API、LLM、Redis 等依赖，按需使用 Mock。
- 避免单元测试直接依赖真实网络和生产数据库。

### 4.3 FastAPI 接口测试

API 测试至少考虑：

- 正常请求及正确响应。
- HTTP 状态码。
- 请求参数校验。
- 响应体结构。
- 404、422 等错误场景。
- 如果存在认证授权机制，还需要测试 401、403 等场景。

异步接口测试优先使用 pytest + HTTPX AsyncClient + ASGITransport。

涉及应用 lifespan 的测试，应正确初始化和清理应用生命周期资源。

使用 FastAPI `dependency_overrides` 替换依赖时，测试结束必须恢复原始依赖配置。

### 4.4 数据库测试

数据库集成测试应验证：

- CRUD 操作。
- 唯一约束与外键约束。
- 事务提交与异常回滚。
- ORM 模型与真实数据库结构的一致性。
- Alembic 迁移能否在干净测试数据库上正确执行。

测试之间必须保持数据隔离。

不得假定普通的 Session rollback 能撤销已经提交的事务；应根据 SQLAlchemy 事务行为设计可靠的隔离和清理机制。

### 4.5 股票分析业务专项测试

股票趋势分析相关逻辑应重点验证：

- 涨跌幅计算正确性。
- MA、EMA、MACD 等指标的计算正确性。
- 历史行情不足时的处理。
- 空数据、重复日期和缺失值处理。
- DECIMAL 精度与数值边界。
- 股票代码重复导致的数据库约束异常。
- PATCH 部分更新时未传入字段保持不变。
- 显式传入 `None` 与未传入字段的不同处理。
- 外部行情 API 超时、异常响应及数据缺失。

测试技术指标时应使用独立确认的参考结果，不得使用被测试函数自身生成预期答案。

## 5. 测试覆盖率规范

使用 pytest-cov 统计覆盖率。

推荐命令：

`uv run pytest --cov=app --cov-branch --cov-report=term-missing`

如果实际 Python 包路径不同，应按照项目结构调整覆盖率目标。

要求：

- 优先覆盖核心业务逻辑及高风险代码。
- 关注分支覆盖率，不只关注行覆盖率。
- 不得为了提高覆盖率编写无实际意义的测试。
- 项目初期不强制规定统一覆盖率百分比。
- 在测试体系稳定后，根据基线逐步设置合理的质量门槛。

覆盖率高不等于业务正确，不能替代测试用例质量审查。

## 6. 开发与检查流程

### 6.1 开始修改之前

Agent 应：

1. 阅读项目现有结构和相关代码。
2. 检查现有 `pyproject.toml`、测试目录和质量配置。
3. 优先复用已有工具、fixtures 和测试模式。
4. 明确本次修改可能影响的功能及已有测试。
5. 保持与现有 FastAPI 分层架构、依赖注入方式一致。

### 6.2 修改代码期间

- 新增业务功能时，同步补充测试。
- 修复 Bug 时，优先编写能够复现该 Bug 的回归测试。
- 修改 API Schema 时，检查对应的参数校验测试。
- 修改 Repository 时，检查数据库集成测试。
- 修改异步代码时，检查 await、异常传播及资源清理逻辑。
- 不得无理由修改与当前任务无关的代码。

### 6.3 完成修改之后

根据变更范围，依次执行：

1. `uv run ruff check .`
2. `uv run ruff format --check .`
3. `uv run pyright`
4. `uv run pytest -v`

必要时进一步执行：

`uv run pytest --cov=app --cov-branch --cov-report=term-missing`

如果只修改了局部代码，可以先运行对应测试，再根据变更影响范围运行完整测试。

如项目暂未安装某项工具或尚未配置对应环境，必须说明原因，不得虚构检查结果。

## 7. CI 质量门禁规范

当项目配置 CI 后，应自动执行：

- 依赖环境安装与锁文件验证。
- Ruff 静态检查。
- Ruff 格式检查。
- Pyright 类型检查。
- pytest 单元测试。
- FastAPI API 测试。
- 必要的数据库集成测试。
- 按项目策略执行覆盖率及安全检查。

CI 使用与项目一致的 Python 版本及 uv 锁文件。

CI 中应优先使用 `uv sync --locked` 安装依赖，减少环境不一致问题。

CI 不得连接或修改生产数据库。

当必要的质量检查失败时，应修复问题后再合并代码，而不是通过忽略错误绕过门禁。

## 8. Agent 修改代码的行为约束

### 必须遵守

- 优先最小范围修改，避免无关重构。
- 保留现有业务行为和 API 契约，除非任务明确要求改变。
- 修改代码时同步考虑类型检查和测试影响。
- 优先复用已有测试 fixtures 和依赖注入机制。
- 测试应可重复执行，不依赖运行顺序。
- 对新增依赖说明必要性，并通过 uv 管理。
- 根据实际执行结果如实报告检查状态。

### 禁止行为

- 禁止删除失败的测试来制造全部通过的结果。
- 禁止随意修改测试预期值以迎合错误的实现。
- 禁止通过大范围 `noqa`、`type: ignore` 掩盖问题。
- 禁止无理由降低 Ruff、Pyright 或 pytest 的配置标准。
- 禁止测试访问生产数据库或使用生产密钥。
- 禁止未经允许执行破坏性数据库操作。
- 禁止在单元测试中依赖不稳定的真实外部 API。
- 禁止将未经执行的检查报告为通过。
- 禁止未经要求大规模调整现有项目架构或重写测试体系。

## 9. Agent 交付与自检要求

完成代码修改后，必须简要汇报：

1. **修改内容**：哪些模块发生变化。
2. **测试变化**：新增或调整了哪些测试用例。
3. **静态检查**：Ruff、Pyright 的执行结果。
4. **测试结果**：pytest 的通过、失败或跳过情况。
5. **未完成事项**：由于环境或依赖限制尚未验证的部分。
6. **剩余风险**：可能影响后续开发或部署的问题。

所有检查结果必须基于真实工具执行。

如果当前任务只要求分析或编写方案、未要求修改项目，则不应擅自安装依赖、修改文件、运行数据库迁移或启动外部服务。

## 10. 执行优先级

Agent 应根据项目成熟度和任务风险分阶段落实规范：

- **P0：基础保障**：Ruff、Pyright、pytest、pytest-asyncio、Mock、必要的 API 测试。
- **P1：工程完善**：pytest-cov、数据库集成测试、pip-audit、CI、pre-commit。
- **P2：进阶质量保障**：Bandit、性能测试、OpenAPI 自动化测试、进一步的运行时可观测性。

优先确保 P0 工具能真实执行，再逐步扩展 P1 和 P2。

**最终目标：让每一次代码变更都能够被检查、验证和追溯，持续降低回归风险，保证 FastAPI 后端项目的正确性、可维护性与可扩展性。**
