# AGENTS.md — 全栈项目工程开发、质量保障与交付规范

> 面向 Codex 等 AI Coding Agent。  
> 适用于：包含 Python/FastAPI 后端、Vue 或 React 前端、数据库及可选 Docker/CI 的项目。  
> 本文件规定**执行行为与验收要求**，不是技术教学材料。学习解释请参阅《全栈项目工程质量保障_学习指南.md》。

## 0. 指令效力与适用原则

- **MUST**：必须遵守；**SHOULD**：正常情况下应该遵守，偏离时说明理由；**WHEN APPLICABLE**：仅在项目确有该模块/工具/环境时适用。
- **先调查，后执行。** 以仓库中实际存在的目录、配置、锁文件、测试与 API 契约为事实依据。不得把本文示例结构、技术选型或命令当作仓库已经实现的功能。
- 遵守用户当前任务、仓库已有规则及更高优先级指令。若规范冲突，应说明冲突并选择风险更低、变更更小的方案。
- 只修改为完成任务所必需的文件；默认不进行无关重构、批量格式化、升级全部依赖或引入新框架。
- **未经明确授权，不部署生产、不操作生产数据、不执行会删除实际数据的命令。** 本地、CI、Staging、Production 必须严格区分。
- 不得为“让 CI 变绿”而删测试、改弱断言、隐藏错误、无理由增加全局忽略或伪造检查结果。

## 1. 项目接管与现状识别

开始工作前，MUST 按需检查：

1. `README.md`、本文件以及相关目录中的其他 `AGENTS.md`。
2. 根目录结构、前端与后端入口、现有运行/构建/测试命令。
3. Python 的 `pyproject.toml`、`uv.lock`、`.python-version`，或项目已采用的其他依赖方案。
4. 前端的 `package.json`、现有 lockfile（`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock` 等）、构建配置和脚本。
5. 后端 Router/Service/Repository/Schema/模型/依赖装配，以及前端页面/组件/API Client/Store。
6. `alembic.ini`、`alembic/env.py`、迁移版本、数据库配置；若存在 Docker Compose、Dockerfile、CI 配置亦应确认。
7. Git 工作区是否包含用户未提交的改动。不得覆盖、回滚、清理与本任务无关的工作。

如果已有规范或工具链，SHOULD 优先复用；没有时才根据任务范围提出或实施最小必要补充。分析任务**只读优先**，不擅自安装、启动、修改或部署。

## 2. 需求拆解、验收标准与实施计划

- 修改前明确：用户目标、受影响模块、API/数据库/前端兼容性、验收标准、测试策略和风险。
- 复杂任务 SHOULD 形成简短计划：拟修改文件、实施顺序、验证项、潜在回滚方案。
- 新功能 MUST 覆盖正常、边界与异常行为，特别是权限、重复提交、并发、外部依赖失败及数据一致性。
- 修复 Bug SHOULD 先补能复现问题的回归测试，再最小化修改实现。
- 未定义的产品行为（例如重复股票的冲突码、`null` 是否表示清空字段）不得臆造；先从现有接口与测试推断，无法确认时公开说明假设。
- 对可能破坏现有数据或公共 API 的更改，MUST 明确影响面并获得相应授权。

## 3. 系统架构与 API 契约

### 3.1 后端职责分层

默认遵循项目已有的分层；若项目采用以下结构，应保持：

```text
Router → Service → Repository → SQLAlchemy Session → Database
```

- **Router**：HTTP 路由、请求/响应 Schema、状态码、身份信息传递，不直接写复杂业务 SQL。
- **Service**：业务规则、组合调用、事务边界协作及可测试的业务决策。
- **Repository**：数据访问、ORM 查询、持久化实现；不承担 HTTP 语义。
- **Schema**：Pydantic 请求/响应边界；区分 Create、Read、Patch/Update 的必要字段与约束。
- **Dependencies**：如果现有项目在 `dependencies.py` 集中装配依赖，MUST 继续遵循；不得把 Repository 直接注入 Router 绕过既定层次。
- **事务**：遵守现有事务所有权；不要让 Router、Service 和 Repository 在同一次业务调用里各自无协调地 `commit()`。

### 3.2 前端职责分层

- 服从项目已有 Vue/React 选型、TypeScript 策略、路由、状态管理和样式系统；MUST NOT 无关替换技术栈。
- 页面负责组合视图，复用组件负责展示/交互，API Client 负责 HTTP 请求与错误归一化；共享状态通过已采用的 Store/Context/Composables 管理。
- 组件应具有可理解的 props/类型、加载/空态/错误态和必要的无障碍语义；禁止仅“视觉上能点”但缺失实际状态处理。
- 涉及视觉改造，SHOULD 遵循现有 Design Tokens/组件库，避免随意新增全局样式覆盖。

### 3.3 前后端契约

- REST 资源路径优先使用名词：`GET /stocks`、`POST /stocks`、`PATCH /stocks/{id}`、`DELETE /stocks/{id}`；有明确业务动作的 Agent/RAG 命令端点不必强行套用 CRUD。
- 明确请求字段、响应 Schema、分页/排序、认证、错误码和日期时间格式；必要时使用 OpenAPI 作为契约来源。
- API 变更时 MUST 同步检查前端调用、Schema、服务逻辑、接口测试以及文档。不能只修改任意一端后声称“前后端完成”。
- PATCH 部分更新 SHOULD 使用 `model_dump(exclude_unset=True)`（或等效方式），区分**未传字段**与**明确传 `null`**；数据库 `NOT NULL` 字段不得被无校验地写入 `None`。
- HTTP 状态码符合明确的接口约定。错误不得默默返回成功，响应不得泄露内部堆栈、数据库凭据或密钥。

## 4. 开发环境与依赖管理

### 4.1 Python（WHEN APPLICABLE）

- 项目已有 uv 时 MUST 继续使用 `pyproject.toml` + `uv.lock`；使用 `uv add` 管理必要新依赖，开发工具使用 `uv add --dev`。
- 锁文件与依赖声明同时更新并提交；CI 优先运行 `uv sync --locked` 或等效的锁定安装。
- Python 版本与项目声明保持一致；不因示例命令而擅自变更运行版本。
- 不将 `.venv/`、真实 `.env`、密钥、缓存或运行日志提交 Git；配置项用 `.env.example` 示例说明。

### 4.2 前端（WHEN APPLICABLE）

- 只使用仓库已经选定的包管理器。`package-lock.json` 对应 npm，`pnpm-lock.yaml` 对应 pnpm；其他锁文件同理。
- 在 CI 中使用可复现安装（如 `npm ci`、`pnpm install --frozen-lockfile`）。
- 新依赖 MUST 说明必要性；不要同时加入功能重叠的状态管理、表单、测试或 CSS 框架。
- 对依赖升级造成的构建、类型及测试变化必须验证。

### 4.3 本地容器服务（WHEN APPLICABLE）

- Docker Compose SHOULD 用于本地开发/联调的 MySQL、Redis 等多服务管理，优先复用现有 `compose.yaml`。
- 使用项目已有 service 名、端口和环境配置，不能猜测外部服务已运行。
- Docker 不等于部署；Compose 不自动提供数据库测试数据隔离。
- `docker compose down -v`、清空卷、删除数据库等可能破坏数据的操作 MUST 明确目标环境、影响范围并取得授权。

## 5. 后端实现规范

- 复用已有 Pydantic Settings、SQLAlchemy 2.x API、异步引擎和统一异常处理；不要平行创建另一套不受管理的连接池或配置系统。
- 异步 I/O 使用 `await`，阻塞 I/O 不应无意识阻塞事件循环。
- `AsyncSession` 不应在并发任务之间共享；请求结束后遵守连接/Session 的清理机制。
- 路由中的响应模型与实际返回值保持一致；输入校验、业务错误、资源不存在与权限不足采用明确的状态码。
- 对外部股票 API、LLM、Redis 等调用，按需要考虑超时、重试边界、限流、失败降级和资源释放；禁止无限重试。
- 日志 SHOULD 使用统一项目日志体系，避免用无上下文 `print` 代替结构化记录；日志不得输出密钥或隐私数据。

## 6. 前端实现规范

- 复用已选 Vue/React、组件库、构建系统及项目布局；新增 UI 应兼顾响应式、键盘操作和交互反馈。
- TypeScript 类型必须与后端 API 契约一致；避免在关键数据边界用 `any` 掩盖不确定性。
- API Client 统一管理 base URL、超时、鉴权、错误映射；不得在多个页面复制不一致的 HTTP 逻辑。
- 对所有异步交互考虑 Loading、Error、Empty、Success；提交动作应避免无意重复触发。
- 需验证 401/403/404/409/422/500、超时及网络断开等已定义的用户体验，不可简单吞掉错误。
- 不应把 CORS 配置当作解决所有请求错误的万能手段；422 优先核对请求数据，跨源错误应核对 Origin 和预检/凭证设置。

## 7. 数据库模型、事务与 Alembic

- 表、字段、索引、唯一/外键约束以**实际 ORM 定义和 Alembic 迁移**为准；不得假设某股票表一定是 `symbol` 唯一或 `(market, symbol)` 联合唯一。
- Schema 变化 MUST 创建/更新迁移脚本，并考虑已有数据、向后兼容、备份及失败恢复。
- 允许使用 `Base.metadata.create_all()` 做某些临时 ORM 测试，但**不得用它代替 Alembic 迁移测试**。
- Alembic `sql=True` 表示生成离线 SQL；需要验证建表或升级效果时，MUST 在隔离的真实数据库中执行在线迁移。
- 生产迁移需要单独审批；不要对生产环境随意执行 `downgrade`、drop、truncate 或自动清库。
- 测试环境必须能显式指定安全的测试数据库 URL；当目标地址不明确时，MUST 停止破坏性数据库动作，不能自动回退到真实业务库。

## 8. 静态质量与格式检查

### 8.1 Python

现有项目有这些工具时 MUST 使用其现有配置；新配置需在任务授权范围内逐步引入。

```bash
uv run ruff check .
uv run ruff format --check .
uv run pyright
```

- Ruff：代码规则检查、import 排序与格式规范。
- Pyright：类型检查；新项目默认推荐 `standard`，升级 `strict` 需评估现有告警。
- 不得为绕过问题批量增加 `# noqa`、`# type: ignore`、全局关闭规则。
- `ruff check --fix` 或 `ruff format` 会修改文件；Agent 仅在修改任务范围内执行，并检查 diff。CI 使用只检查的命令。

### 8.2 前端

- 如果项目已配置，运行 ESLint、TypeScript/`vue-tsc`、Prettier 检查或对应项目脚本。
- 只执行 `package.json` 真实存在的脚本；关键质量门禁缺失时应指出，不得用 `--if-present` 掩饰“其实没有检查”。
- 不得无理由引入 ESLint/Prettier 与现有格式化配置冲突的规则。

## 9. 自动化测试：用例与分层

### 9.1 基本原则

- 测试用例应具有明确目标、输入/前置条件、执行步骤和预期结果。
- 核心功能 MUST 覆盖正常、边界、异常至少三类关键路径，具体数量以风险为准。
- 单元测试保持快速、可重复、尽量不访问真实网络/数据库。
- 回归测试应验证所修复的缺陷不会复发。
- 禁止只有函数调用却没有有意义断言；禁止使用空洞的 `assert True` 代替行为验证。

### 9.2 后端测试

- pytest 负责组织执行和断言；`pytest-asyncio`（或现有 AnyIO 方案）负责异步测试，避免无意义混用。
- `unittest.mock` 的 `Mock`、`AsyncMock`、`patch` 可以替换外部 API/LLM/第三方服务；Mock 不得代替所有关键数据库集成测试。
- 使用 `pytest.mark.parametrize` 覆盖输入组合、使用 `pytest.raises` 验证预期异常。
- API 测试可用 FastAPI TestClient 或 pytest + HTTPX `AsyncClient`/`ASGITransport`；HTTPX 是 HTTP 客户端，不是测试执行框架。
- API 测试至少校验状态码、响应结构、校验失败、权限/认证（若有）与核心异常；需要 lifespan 初始化的应用 MUST 明确管理生命周期。
- 采用 FastAPI `dependency_overrides` 后测试结束 MUST 恢复原有配置。

### 9.3 前端测试

- 已采用 Vitest/Jest 等工具时复用已有组件测试框架；测试表单、条件渲染、Loading、错误提示、状态更新。
- Playwright（若已引入或有任务要求）用于重要浏览器 E2E 流程，至少考虑关键业务从 UI→API→测试数据的联动。
- 可以在 UI 单元测试中 Mock API，但不得把所有前后端联调都替换成 Mock。

### 9.4 覆盖率

- pytest-cov（若已引入）统计行/分支覆盖率，例：`uv run pytest --cov=app --cov-branch --cov-report=term-missing`。
- 不以“总覆盖率越高越好”代替业务风险判断；不为凑覆盖率修改业务逻辑或编造无意义断言。
- 前端覆盖率报告须使用项目现有工具；不强制两端采用同一百分比门槛。

## 10. 数据库集成测试：Compose、Testcontainers 与 fixtures

- **Docker Compose**：适合可常驻的本地/集成环境；**Testcontainers**：适合 pytest 自动创建/回收隔离容器。可并存，但不能无必要地同时引入两套重复测试服务。
- MySQL 生产环境关键查询/约束 SHOULD 在 MySQL 测试环境验证，而不是仅用 SQLite 或 Mock。
- 集成测试 MUST 连接测试专用库，不得连接开发或生产库；凭证应为测试专用，并避免被提交到仓库。
- `pytest.fixture` 负责创建、注入和清理测试资源；`yield` 后通过 `finally` 确保连接和容器资源释放。
- 可以 session 级复用测试容器，但每个用例的数据仍需隔离；不得依赖不稳定的执行顺序。
- 普通的 `session.rollback()` **未必能回滚代码已提交的事务**；需要验证外层事务/SAVEPOINT 或采用独立数据库、记录清理、重建等策略。
- MySQL DDL 和 Alembic 迁移测试通常不能依赖普通事务回滚恢复初始数据库。
- Testcontainers 依赖 Docker Engine 或兼容运行环境；没有容器访问权限时如实报告未能执行，不得假称通过。

### 数据库测试最低关注点

- ORM CRUD、过滤/排序/分页、唯一约束、外键、`NOT NULL`、数值精度。
- 事务提交与失败回滚、异常传播、并发情况下的数据一致性（按需求）。
- 通过 Alembic **在线**升级后验证表、索引、约束和 `alembic_version`；如业务要求支持降级，应在独立可销毁测试库验证降级。
- 针对股票业务：非法/重复 symbol，日线日期唯一性（以实际索引为准），指标数据不足，PATCH `None` 与未提交字段的区别。

## 11. 前后端联调与验收

- 一项跨端功能 MUST 至少验证：前端请求字段、后端 Pydantic 校验、状态码/响应格式、前端成功与错误显示。
- 按需检查跨域来源、预检、cookies/credentials、代理配置；不能通过永久放开所有生产 Origin 掩盖错误。
- 用户关键路径 SHOULD 做真实端到端验证，重点关注创建、列表刷新、失败处理和权限边界。
- 用户报告“界面很丑/交互失效”时，必须检查视觉一致性与实际交互流程，不能只更新截图或静态 CSS 而不验证功能。
- 对不稳定外部服务采用受控 Mock / 测试替身；正式联调阶段根据权限和成本验证真实依赖。

## 12. Git 协作与代码审查

- 开始前检查 Git 工作区；避免覆盖他人的改动。
- 新功能 SHOULD 使用独立分支和小粒度提交；Commit/PR 描述实际变更、风险、验证结果和迁移影响。
- 不提交生成的密钥、真实个人数据、数据库备份、依赖缓存或无必要的大型构建产物。
- 有变更影响公共 API、数据库或部署策略时，MUST 在 PR 中明确兼容性与回滚风险。
- Code Review 与自动化检查互补；测试通过不代表业务设计或安全性必然正确。

## 13. CI：持续集成与质量门禁

- CI 可使用 GitHub Actions 或仓库现有平台。不得为了换平台擅自迁移。
- CI 应在 PR/Push 上执行适当的静态检查、类型检查、单元测试、API 测试和前端构建验证；数据库集成测试需要先准备隔离服务。
- Python 优先采用 `uv sync --locked`；前端采用现有锁文件对应的确定性安装命令。
- 可将后端 Lint/Types/Tests、前端 Lint/Types/Tests/Build、数据库 Integration Tests 拆成 Job 并行；不强制所有耗时测试在每次本地保存时执行。
- CI 工作流遵守最小权限，第三方 Action SHOULD 固定受审查的提交 SHA，并定期维护版本。
- 只有真正配置 required checks 和 Branch Protection / Rulesets，失败状态才能成为强制合并门禁。不能声称 CI 失败本身阻止 `git push`。
- CI 配置更改后应验证触发条件、退出码、缓存/锁文件和运行器所需环境；不得将缺失服务的失败报告成“测试全通过”。

## 14. 构建、持续交付与部署

- **CI**：验证代码能否安全集成；**Continuous Delivery**：保持可发布状态、通常保留生产发布决定；**Continuous Deployment**：满足门禁后无需逐次人工批准自动上线。
- Docker 镜像或前端静态资产是**部署产物**，构建成功不等于已经部署成功。
- 生产发布 SHOULD 优先采用：CI → 构建一次不可变版本 → Staging → 冒烟/E2E → 审批 → 推广同一版本到 Production。
- 不得在没有授权和部署配置时自动执行生产发布、数据库迁移或覆盖线上镜像。
- 发布前必须考虑：密钥注入、环境隔离、健康检查、流量切换、兼容性、备份、应用回滚与数据恢复。
- 数据库迁移可能不可逆；应用回滚不意味着数据库可以安全 `downgrade`。对破坏性变更先设计兼容迁移和恢复方案。

## 15. 生产运行、异常诊断与安全

- 生产服务 SHOULD 有适合当前规模的健康检查、结构化日志、错误监控、关键指标和告警。
- 出现故障时先保护数据和用户影响范围，再根据日志、请求 ID、错误率、延迟和依赖服务状态定位。
- 需要安全扫描时可采用 `pip-audit`、`Bandit` 及前端依赖审计；其职责不同于单元测试，不得宣称单一扫描证明系统安全。
- API Keys、数据库密码、Token 和真实用户数据不得出现在代码、测试日志、截图、错误响应和文档示例中。
- 不得在缺少足够证据时强行判断根因，也不得将未知结果描述为已经修复。

## 16. 修改完成后的验证与交付报告

### 16.1 条件性验证矩阵

根据**实际改动范围**执行，不是无条件把所有命令跑一遍：

| 改动类型 | 主要检查 |
|---|---|
| 纯 Python 逻辑 | Ruff、Pyright、对应 pytest 单元测试 |
| FastAPI API/Schema | 上述检查 + API 测试 + 与前端契约核对 |
| SQLAlchemy/Model/迁移 | 上述检查 + 独立真实 DB 集成测试 + 必要时 Alembic 在线迁移测试 |
| Vue/React 组件 | ESLint、TS/`vue-tsc`、已有组件测试、构建 |
| 前后端共同修改 | 双端检查 + API 契约验证 + 适当联调/E2E |
| CI/构建/部署 | 工作流语法与触发逻辑、锁文件、构建和环境隔离验证；不得无授权生产部署 |

Python 示例命令（**仅在对应工具已安装且目录存在时使用**）：

```bash

uv run ruff format --check .
uv run pyright
uv run pytest -v
uv run pytest --cov=app --cov-branch --cov-report=term-missing
```

前端按已有包管理器和 `package.json` 脚本执行，例如：

```bash
npm ci
npm run lint
npm run typecheck
npm run test
npm run build
```

若前端实际使用 pnpm 或其他包管理器，MUST 使用仓库对应的命令。若脚本不存在，不要无声跳过并宣称已验证。

### 16.2 交付汇报模板

每次完成代码修改后，最终回复 MUST 简洁说明：

1. **实现内容**：改了哪些模块、为什么。
2. **测试变更**：新增/修改了什么测试，覆盖哪些正常、边界、异常行为。
3. **检查结果**：每条已执行的静态检查、类型检查、测试和构建命令及真实结果。
4. **未执行/阻塞项**：缺工具、Docker 不可用、缺密钥、无测试数据库等必须如实注明。
5. **兼容性与风险**：涉及 API、Schema、迁移、权限、部署的潜在影响及后续措施。

**禁止**将未执行写成 PASSED，禁止把局部单元测试通过写成“全栈验收通过”。
